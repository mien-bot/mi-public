# Agent harness maintenance

Repository instructions and generated workspace instructions serve different scopes.
[AGENTS.md](../AGENTS.md) governs source development; private workspaces receive instructions
generated from the canonical templates below.

| Workspace | Template | Generator |
| --- | --- | --- |
| Project | `installer/agent-harness/common-rules.md` | `electron/agentHarness.js` |
| Firm planning | `installer/agent-harness/firm-common-rules.md` | `electron/firmHarness.js` |
| Lead | `installer/agent-harness/lead-common-rules.md` | `electron/leadHarness.js` |
| Permit QA/QC | `installer/agent-harness/permit-qaqc-common-rules.md` | `electron/permitQaqcHarness.js` |

Each generator renders both `AGENTS.md` and `CLAUDE.md` from its template and records the
canonical rules hash. Edit the template once; do not patch either generated file directly.
Personal-workspace instructions are generated separately by `electron/personalAgentContext.js`.
Keep mirrored project prompts in `lib/agentContext.ts` and `electron/agentContext.js` aligned
when changing runtime prompt behavior.

## Refresh and verification

1. Edit the source template and relevant public documentation. Keep examples synthetic and
   preserve confirmation rules, workspace boundaries, and the read-only chat contract.
2. Run the harness tests using temporary fixture roots. Verify both generated instruction
   files contain the policy and that refresh preserves memory, evidence, and inbox entries.
3. A source edit affects only runtimes using that source. Installed copies need a separately
   built and verified update before they can emit the revised template.
4. For an authorized real workspace, use Mi's Repair/Refresh Agent Workspace flow. Review
   conflicts and preserve user-authored files; do not repair conflicts by replacing memory.
5. Verify the resulting instructions and canonical hash. Record exactly which workspaces
   were refreshed. A test fixture is not evidence that live workspaces were updated.

The documentation/template update in this repository does not refresh any live workspace,
install an app, change integrations, or upgrade dependencies.

## Formal submissions

Formal submission PDFs must not contain the Mi mark, logo, or Generated by Mi footer.
This covers city/permit/agency submissions, drawings, Form 400, Form 408R, REScheck, and
supporting files. Prepare clean copies from originals or designated flattened/signed sources;
preserve signatures, seals, drawing scale, and content. Check all PDFs in the actual upload
folder, including earlier copies. Branded internal backups belong outside that folder.

Do not use `brand-pdf.ps1`, Export PDF with Mi mark, or the automatically branded staged
Notion-task PDF flow for formal submissions. The existing pipeline has no documented clean
submission mode; this instruction change does not add one. Use a separate approved clean
workflow, and report a limitation rather than silently delivering a branded submission.

Internal review PDFs remain eligible for branding. Until the PDF dependency advisories are
resolved and verified, do not feed untrusted PDFs to Mi helpers, including URL-to-PDF fetches.
