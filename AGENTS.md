# Mi public repository instructions

This is the public source edition. Read [the start guide](docs/agent-start-here.md),
[architecture](docs/code-structure-guide.md), and [open review findings](docs/public-review.md)
before editing. Follow the user's exact task scope and preserve unrelated changes.

## Privacy and authority

- Never import private repository history, internal documentation, real client/project records,
  credentials, chat archives, snapshots, or generated workspace context. Use synthetic fixtures.
- Run `git status --short --branch` before editing and before handoff. Stage named files only.
- Project `notion_page_id` and `dropbox_path` values are human-confirmed; never infer them.
- AI output is a draft until the person confirms the exact write. Technical access is not
  authorization to mutate Notion, Dropbox, or shared records. Report partial writes honestly.
- Keep credentials out of renderer APIs, logs, diagnostics, Git, and unrelated subprocesses.
- Do not restore missing internal docs from another checkout. Write public guidance from code.

## Formal submission PDFs: no Mi branding

City, permit, agency, and other formal submission PDFs must have no Mi mark, logo, or
Generated by Mi footer. Include drawings, Form 400, Form 408R, REScheck, and supporting files.
Use original or user-designated flattened/signed sources; preserve signatures, seals, scale,
and content. Check every PDF in the actual upload folder, including earlier copies. Keep
branded internal backups outside it. Never run the branding helper on submission copies.

Update canonical templates under `installer/agent-harness/` and use the supported workspace
refresh flow; never hand-edit generated instructions. The current staged Notion-task PDF
pipeline brands output and must not finalize formal submissions.

## Implementation and verification

- Read the relevant installed guide under `node_modules/next/dist/docs/` before changing
  Next.js code. Do not assume behavior from another framework version.
- Keep `lib/agentContext.ts` and `electron/agentContext.js` behavior synchronized.
- Preserve scoped paths, confirmation checks, conflict detection, durable writes, and
  user-authored memory. Never attach two resizing terminal views to one PTY session.
- Keep servers on loopback. The known dependency advisories in the review remain unresolved;
  passing tests do not establish safe deployment or safe untrusted-document processing.
- Run focused tests during development. The integration gate is `npm run lint`, `npm test`,
  `npm run validate-content`, `npm run build`, and `git diff --check`.
- A desktop UI claim requires an actual desktop window check plus browser fallback where
  relevant. Use a temporary canonicalized profile and free `STUDIO_ELECTRON_PORT`; never use
  a real user's profile, credentials, or project records. Run only one dev server per checkout.
- Do not claim packaging, signing, installation, cloud sync, or workspace refresh unless verified.

Handoffs include branch/base, final commit, changed files, checks, limitations, external writes,
and confirmation that unrelated/private files were preserved.
